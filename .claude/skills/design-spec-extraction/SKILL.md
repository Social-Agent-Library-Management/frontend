# Design Spec Extraction

디자인을 구현 가능한 스펙으로 번역하는 절차. 목적은 구현팀(component-architect, frontend-implementer)이 **추측 없이 착수**할 수 있는 명세를 만드는 것이다.

## 1단계: 입력 형태 판별

디자인 참조는 네 가지 형태로 온다. 형태에 따라 추출 전략이 다르다.

| 입력 형태 | 전략 |
|----------|------|
| 내보낸 React/JSX 코드 | 가장 정확. 구조·className·props를 그대로 인용하되 인라인 중복을 패턴으로 묶는다 |
| 디자인 URL (claude.ai/design 등) | 접근 가능하면 렌더된 구조를 읽고, 불가하면 사용자에게 코드/스크린샷 요청 |
| 스크린샷 이미지 | 시각적으로 레이아웃·색·간격을 추론. 상태/상호작용은 대부분 "미확정"이 됨 |
| 텍스트 설명 | 요구를 구조화하되 시각 세부는 사용자 확인 대상으로 표시 |

입력 형태를 특정할 수 없으면 지어내지 말고 사용자에게 되묻는다. 잘못된 스펙은 파이프라인 전체를 오염시킨다.

## 2단계: 레이아웃 트리 분해

화면을 중첩 구조로 옮긴다. 섹션 → 영역 → 요소 순으로, 각 노드에 역할을 붙인다.

```
Page (대시보드)
├─ Header (고정 상단)
│  ├─ Logo
│  ├─ Nav (링크 4개 — 반복)
│  └─ UserMenu (아바타 + 드롭다운)
├─ Sidebar (좌측, md 이상에서만 표시)
│  └─ NavItem × 6 (반복 — 중복 후보)
└─ Main
   └─ StatCard × 4 (반복 — 중복 후보)
```

**반복을 세는 것이 핵심이다.** 같은 형태가 N회 나오면 `× N (반복 — 중복 후보)`로 즉시 표시한다. 이것이 다음 단계(재사용 설계)의 출발점이다.

## 3단계: 디자인 토큰 식별

픽셀이 아니라 **토큰 관점**으로 옮긴다. 이 프로젝트는 Tailwind v4이므로, 토큰은 나중에 `globals.css`의 `@theme`에 CSS 변수로 들어간다. 스펙에서는 의미 있는 이름으로 정리한다.

| 범주 | 추출 항목 | 예 |
|------|----------|-----|
| 색상 | 배경/전경/주요/보조/경계/상태색 | primary, surface, muted, danger |
| 타이포 | 폰트 패밀리, 크기 스케일, 굵기, 행간 | heading-lg, body, caption |
| 간격 | 반복되는 간격 값을 스케일로 | xs/sm/md/lg/xl |
| 반경 | border-radius 값 | sm/md/full |
| 그림자 | elevation 단계 | sm/md/lg |
| 브레이크포인트 | 반응형 분기점 | sm/md/lg/xl |

내보낸 코드에 Tailwind 클래스가 있으면 그 값을 그대로 신뢰한다(`bg-blue-600` 등). 스크린샷이면 근사값을 추정하고 "추정"으로 표시한다.

## 4단계: 컴포넌트 인벤토리

화면의 모든 UI 단위를 표로 정리한다. **반복 횟수와 중복 후보 여부**를 반드시 채운다 — 이것이 하네스의 핵심 가치(중복 제거)를 위한 데이터다.

```
| 컴포넌트 | 설명 | 반복 | 중복 후보 | variant 힌트 |
|----------|------|------|----------|-------------|
| StatCard | 지표 카드 | 4 | 예 | 색상별(4종) |
| NavItem  | 사이드바 항목 | 6 | 예 | active/기본 |
| Button   | 주요 액션 | 3 | 예 | primary/ghost |
| PageHeader | 상단 제목 영역 | 1 | 아니오 | — |
```

미묘하게 다른 반복(예: 색만 다른 카드 4개)은 "variant 힌트"에 차이를 적어, 아키텍트가 하나의 컴포넌트 + variant로 통합할지 판단하게 한다.

## 5단계: 상태 & 상호작용

정적 스크린샷은 상태를 숨긴다. 각 상호작용 요소에 대해 다음을 명시하거나 "미확정"으로 남긴다:
- 인터랙션 상태: hover / focus / active / disabled
- 데이터 상태: loading / empty / error / success
- 동작: 클릭 시 무엇이 일어나는가(네비게이션/토글/제출)

확인되지 않은 상태를 지어내지 않는다. "미확정 — 확인 필요"가 잘못된 확신보다 낫다.

## 6단계: 반응형 규칙

브레이크포인트별 레이아웃 변화를 기술한다.
```
- base(모바일): 단일 컬럼, Sidebar 숨김, StatCard 세로 스택
- md 이상: Sidebar 표시, StatCard 2열
- lg 이상: StatCard 4열
```

## 7단계: 데이터/콘텐츠 형태

화면이 표시하는 데이터의 shape을 추론한다. 이것이 구현자의 TypeScript 타입이 된다.
```
StatCard 데이터: { label: string; value: number; delta: number; trend: 'up'|'down' }
NavItem 데이터: { label: string; href: string; icon: string; active?: boolean }
```

## 출력

`_workspace/01_design-spec.md`에 아래 섹션 순서로 저장한다:
개요 → 레이아웃 트리 → 디자인 토큰 → 컴포넌트 인벤토리 → 상태 & 상호작용 → 반응형 규칙 → 데이터/콘텐츠 형태 → 미확정 항목.

## 원칙 요약
- **사실과 추측을 구분한다.** 확인된 것, 추론한 것, 미확정을 시각적으로 분리 표기.
- **반복을 집요하게 센다.** 중복 후보 표시가 이 단계의 가장 중요한 산출물이다.
- **토큰 관점으로 옮긴다.** 일회성 픽셀값이 아니라 재사용 가능한 스케일로.
- **모르면 되묻는다.** 파이프라인 첫 단계의 오류는 하류 전체를 오염시킨다.
